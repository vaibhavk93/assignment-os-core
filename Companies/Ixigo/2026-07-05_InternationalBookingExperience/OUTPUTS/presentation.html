Problem
A $23–35B market growing 11.4% is being served by a search algorithm trained for a different problem entirely
  • Ixigo's ranking built for domestic traveler: primary variable = price, trust already established (same currency, same docs, home turf)
  • International discovery inverts this: first-time traveler's primary anxiety is "can I get a visa / will my card get declined" — not "cheapest fare"
  • Result: international searches on ixigo convert to a booking on MakeMyTrip — MMT's Atlys visa portal and TripMoney forex card address the actual point of hesitation
  • Distribution is not the bottleneck — ixigo already has 480M users. Relevance is the bottleneck.

Architecture
Three components, not one model: Intent Classifier → Destination Re-Ranker → Proactive Trigger System
1 · Intent Classifier
  • Scores each user's "international-curious" likelihood from behavioral signals: flexible-date searches, cross-sell clicks, KYC passport-validity, prior insurance
  • Estimates first-time vs. experienced traveler status — feeds home-screen + search re-ranking
  • Hardest ML component — 3–6 months data collection before reliable
2 · Destination Re-Ranker
  • Adds visa-friction-adjusted feasibility, forex-decline risk, and trust signals on top of base price ranking
  • Staged approach: base signals → personalization → context signals, each A/B-tested for conversion lift before next layer ships (Airbnb's method)
  • Where the $36.5M ML investment sits
3 · Proactive Trigger System
  • Event-driven: watches for state changes (visa policy update, price drop, visa-status change) → pushes ranked, timed notification
  • Track 1 Bangkok is a narrow, rules-based version of this — no ML needed, ships in 4 weeks
  • Shared infrastructure across both tracks
None of these three components require a conversational interface. Chat could optionally sit on top as one notification channel — but the system delivers value through what is ranked and when it notifies.

Metrics & Measurement
Ranking quality offline → conversion lift online → task completion over NPS — built from global practice, not internal precedent
Pre-Launch · Offline
  • AUC — ranking model discrimination
  • NDCG — ranking quality on held-out historical search data
  • Validate visa-friction-adjusted ranking is better before it touches a live user
Launch · Online
  • pCTR — predicted click-through rate per ranking layer
  • pCVR — predicted conversion rate per ranking layer
  • Staged A/B tests — each layer ships only after prior layer shows conversion lift, not on a fixed calendar
Business Impact
  • Task completion rate — did user complete booking without abandoning at visa/payment step?
  • Booking conversion lift: BKK / DXB / SIN corridors vs. pre-launch baseline
  • International share of total ixigo GMV
Drift monitoring required: ranking models degrade silently as visa rules and user behavior shift. Monthly recheck of model accuracy with explicit alert threshold for retraining (e.g., after a regulatory change like Bangkok's). Ixigo has no existing practice here — must be built alongside the product.
Rollout
Two tracks, not two phases — 4-week Bangkok runs on existing infra while 16-week ML architecture starts in Dubai

Bangkok Visa Alert

  • ~1 backend + 1 product engineer for the sprint

  • Generates real conversion data that de-risks Track 2's Bangkok leg

Full Intent + Re-Ranker + Trigger
  • 4–6 wk: Dubai MVP — visa-on-arrival, no partner dependency
  • 8–12 wk: Bangkok — government API ready, layered on Track 1 data
  • 12–16 wk: Singapore — agent-mediated, highest complexity

Tracks draw on different skill sets — notification/backend engineering vs. ML/data engineering. They don't compete for the same scarce capacity. That's what makes genuine parallelism credible, not a relabeled sequential plan.

Tradeoffs
Three tradeoffs worth naming before the panel asks — self-surfaced, not discovered in execution
Build vs. Partner (Visa/Forex)
  • Recommend: partner for data sourcing, build ranking on top — data feeds proprietary model, not a bolt-on feature à la MMT
  • Exclusivity risk: if MMT-Atlys is exclusive/investment-linked, fallback is VFS Global API or destination govt e-visa API directly
  • Track 1 (Bangkok) scoped to need no partnership at all — sidesteps exclusivity risk for the most urgent corridor
Personalization vs. Privacy
  • Intent classifier inferring "first-time international traveler" from behavioral signals can feel invasive if surfaced clumsily
  • Mitigation: surface as improved relevance (better-ranked results), not visible profiling — the product should feel smarter, not like it's watching you
  • No "because you're a first-time traveler" messaging
India-Specific vs. Global Reusability
  • Architecture tuned to Indian passport rules, INR-forex dynamics, BKK/DXB/SIN — right call for a first build, don't over-engineer for multi-market now
  • Re-ranker and trigger system are corridor-agnostic in design — defer multi-market generalization until India build proves the model
  • Relevant given ixigo's Trenes.com (Spain) + Singapore subsidiary
Build-vs-partner is the riskiest tradeoff: partnership timeline is outside ixigo's control. If Atlys is unavailable → VFS Global or govt API, not waiting.

A2 · Competitive Detail
How MakeMyTrip's visa/forex stack actually works — and why it's not the moat to copy
MMT Visa — Atlys Partnership
  • Investment/partnership relationship with Atlys — a preferential commercial deal
  • Estimated 2–3 month structural head start vs. a competitor negotiating from scratch
  • Possible exclusivity/investment linkage — ixigo may not be able to replicate on similar timeline
  • Integrated as a discrete feature/upsell — not a ranking or personalization signal
MMT Forex — TripMoney
  • TripMoney forex card — standard checkout upsell
  • No public evidence MMT uses forex-decline-risk signals to alter search results or ranking
  • A static feature, not an adaptive layer — this is the structural basis for the leapfrog claim
  • Neither Atlys nor TripMoney alter what results a user sees before actively seeking that product
Structural gap: MMT's advantage is a partnership and feature-availability advantage, not an algorithmic one. No Indian OTA — including MMT — has disclosed ranking sophistication comparable to Airbnb or Booking.com. This is the whitespace.

Source basis, confidence calibration, and what was not done
What Was Done

What Was Not Done

  • No direct UX audit of ixigo's live domestic vs. international checkout flows
  • No access to ixigo's booking-level GMV data to ground the AOV multiplier estimate

Case-study-appropriate methodology given assignment constraints. Real-world execution should validate pain-point prevalence with direct user research — what % of bookers actually experience each friction point and where in the funnel they drop off.
