# Assignment OS — System Architecture (Freeze v0.2)

> Last updated: 2026-07-05. Supersedes v0.1.

---

## 1. Vision

Build an **Assignment Operating System** that maximizes the user's chance of succeeding in interview assignments — not generating polished documents. Every assignment becomes a reusable project with structured artifacts, repeatable workflows, human review at high-value decision points, and long-term knowledge reuse across companies and time.

**Primary optimization target:** Interview success (hiring signal coverage), not output aesthetics.

---

## 2. Core Principles

1. **Company-centric organization** — multiple assignments live under a company; company knowledge is reusable across them.
2. **Every assignment is an independent project/workspace** — isolated context, no bleed between companies.
3. **Artifacts are the source of truth** — not chat history. Every stage produces typed, persisted artifacts.
4. **Agents have one responsibility each** — composable, inspectable, replaceable.
5. **Skills store reusable knowledge; tools perform deterministic work; agents make decisions.**
6. **Human review only at high-value decision points** — smooth default, controlled exceptions.
7. **Token efficiency is first-class** — indexed retrieval, context contracts per agent, summaries alongside full artifacts, no duplicate research.
8. **Recommendations must be evidence-backed or explicitly marked as assumptions.**
9. **Reuse company knowledge with freshness checks** — refresh dynamic info aggressively, stable info rarely.
10. **Optimize for hiring success** — the assignment is not the objective; the hiring signal is.

## 4. Per-Assignment Workspace Structure (Option D — Finalized)

```
<Assignment>/
  INPUT.md              ← immutable: assignment text, JD, media refs, constraints
  WORKSPACE.md          ← human-readable merged view (auto-generated by Workspace Manager)
  workspace/            ← machine-readable section files (what agents actually read)
    intent.md
    hiring_signal.md
    classifier.md
    context.md
    research_plan.md
    research_<q1>.md    ← one file per research question
    research_<q2>.md
    insights.md
    hypotheses.md
    recommendations.md
    tradeoffs.md
    assumptions.md
    decisions.md
    devils_advocate.md
    executive_review.md
    open_questions.md
    next_steps.md
  OUTPUTS/              ← final deliverables: PPT, DOC, speaker notes, appendix, etc.
  MEMORY.md             ← reusable learnings from this assignment
  state.json            ← orchestrator state: current stage, loop count, checkpoint
```

### Indexing rule (finalized)
- Agents ONLY read individual `workspace/<section>.md` files — never full WORKSPACE.md
- Workspace Manager is the only writer to all workspace/ section files
- After each write, Workspace Manager regenerates WORKSPACE.md as a stitched human view
- Each agent's context contract specifies exactly which section files it reads

### state.json schema
```json
{
  "assignment_id": "string",
  "company": "string",
  "current_stage": "string",
  "loop_count": 0,
  "last_checkpoint": "ISO datetime",
  "hitl_nudge_count": 0,
  "status": "active|complete|paused|failed"
}
```

## 5. Media Registry System (Finalized)

### Media storage structure

```
Companies/<Company>/
  media/
    2026-07-05_1430_home_screen.png
    2026-07-05_1430_home_screen.meta.json
    2026-07-05_1431_onboarding_flow.png
    2026-07-05_1431_onboarding_flow.meta.json
  MEDIA_REGISTRY.json
```

Naming convention: `<YYYY-MM-DD>_<HHMM>_<description>.<ext>` — sortable, searchable, auto-timestamped.

### .meta.json schema (per media file)

```json
{
  "id": "string",
  "file": "media/filename.ext",
  "timestamp": "ISO datetime",
  "type": "screenshot|pdf|recording|figma|other",
  "platform": "iOS|Android|Web|null",
  "source_company": "string",
  "competitor": false,
  "competitor_name": "string | null",
  "screen_name": "string",
  "flow": "string | null",
  "description": "string",
  "key_elements": ["string"],
  "analysis_summary": "string",
  "analysis_confidence": "high|medium|low",
  "tokens_used_to_analyze": 0,
  "requires_reanalysis": false,
  "assignments_used_in": ["assignment_ids"]
}
```

### MEDIA_REGISTRY.json schema

```json
{
  "company": "string",
  "last_updated": "YYYY-MM-DD",
  "total_items": 0,
  "media": [
    {
      "id": "string",
      "file": "media/filename.ext",
      "meta": "media/filename.meta.json",
      "type": "screenshot|pdf|recording|figma",
      "summary": "one-line description",
      "competitor": false,
      "competitor_name": "string | null",
      "timestamp": "ISO datetime",
      "assignments": ["assignment_ids"]
    }
  ]
}
```

### Smart media routing logic (agents)

```
Agent needs visual context
↓
Read MEDIA_REGISTRY.json (tiny — always fast)
↓
Filter relevant items by screen/flow/competitor/timestamp
↓
For each relevant item: read .meta.json (small)
↓
Is analysis_confidence "high" AND question answerable from analysis_summary?
├── YES → use summary text only (zero image tokens)
└── NO  → load image → re-analyze with vision → update .meta.json + MEDIA_REGISTRY.json
```

## 6. Skills Library (Finalized List)

Skills are markdown files in `Global/skills/`. Agents reference them in their context — content is loaded into prompt, not dynamically executed.

| Skill file | Contents |
|---|---|
| `hiring-signal-patterns.md` | Known patterns of what companies test at each level; style signals by company type |

**Note:** `writing-style.md` and `hiring-signal-patterns.md` require user input before agents can use them properly. Seed these first with personal preferences.

## 8. Slash Commands (Finalized)

Defined as `.claude/commands/<name>.md` files. Each command is an orchestrator entry point.

| Command | Trigger | What it does |
|---|---|---|

| `/output select` | HITL gate | Choose output formats before Formatter runs |

## 9. Hooks (Finalized)

Configured in `.claude/settings.json`.

### Session-start hook
Fires on every session open.
- Reads CLAUDE.md (project brain)
- Reads state.json if exists → loads active assignment context
- If active assignment: loads Company Memory + current workspace summary into context
- Shows status to user

### Pre-file-read hook
Fires before any agent reads a file.
- Checks agent's declared context contract
- Blocks reads outside contract scope
- Logs attempted reads for auditability

### Post-stage hook
Fires after each agent completes.
- Writes checkpoint to state.json
- Logs stage name + approximate token count + timestamp
- If stage = final: marks assignment complete in state.json

## 10. The Pipeline (17 Stages — Finalized)

Sequential chain with one parallel fan-out at Research.

### Stage 0 — Session Init
**What:** Hooks fire, system loads context, user sees status.  
**Trigger:** Every session open. Not a pipeline stage — always runs.

---

### Stage 1 — Media Intake (optional)
**Agent:** Media Analysis Agent  
**Tools:** Vision, PDF extraction, File write  
**Input:** User-provided files (any format)  
**Process:** Copy to `media/` with timestamp → analyze once (vision or text extraction) → write `.meta.json` → update `MEDIA_REGISTRY.json` → update INPUT.md media refs  
**Output:** Files registered with metadata  
**HITL:** None  

---

### Stage 2 — Input Collection
**Agent:** Intake Agent  
**Tools:** File write  
**Input:** Assignment text (pasted by user), JD, competitor names, constraints  
**Output:** `INPUT.md` structured and complete  
**HITL:** None  

---

### Stage 3 — Hiring Signal Analysis
**Agent:** Hiring Signal Analyzer  
**Model:** Sonnet  
**Skills:** `hiring-signal-patterns`, `assignment-type-templates`  
**Reads:** `INPUT.md`  
**Output:** `workspace/hiring_signal.md`  
**HITL:** None  

---

### Stage 4 — Intent Contract
**Agent:** Intent Agent  
**Model:** Opus  
**Skills:** `pm-frameworks`  
**Reads:** `workspace/hiring_signal.md`, `INPUT.md`  
**Output:** `workspace/intent.md`  
**HITL Checkpoint #1:** Only if confidence < 0.75. User confirms/edits contract.  

---

### Stage 5 — Assignment Classification
**Agent:** Classifier Agent  
**Model:** Haiku  
**Skills:** `assignment-type-templates`  
**Reads:** `workspace/intent.md`, `workspace/hiring_signal.md`  
**Output:** `workspace/classifier.md`  
**HITL:** None  

#### Tiered classifier design (finalized)

Classifier picks from 10 fixed templates. Within each template, stages are optional — classifier sets `skip[]` and `emphasis{}`.

**10 pipeline templates:**
1. `prd` — requirements, edge cases, rollout, metrics, risks
2. `product_teardown` — research, UX analysis, business analysis, prioritization, recommendation
3. `growth_strategy` — market, funnel, levers, experiments, roadmap
4. `metrics_analytics` — KPIs, diagnosis, root cause, experiment design
5. `case_study` — problem, research, framework, recommendation, tradeoffs
6. `market_research` — landscape, segments, sizing, positioning
7. `technical_architecture` — system design, constraints, scalability, tradeoffs
8. `exec_memo` — situation, complication, resolution, action
9. `pricing_strategy` — value metric, tiers, competitive, willingness-to-pay
10. `presentation` — narrative, slides-first, speaker-focused

Adding new agent types: define contract in AGENT_CONTRACTS.md → add to relevant template(s) in `assignment-type-templates.md` → Classifier can now include/skip it. Not auto-invented.

---

### Stage 6 — Execution Budget Estimate
**Agent:** Orchestrator (built-in logic, no separate agent)  
**Reads:** `workspace/classifier.md`  
**Output:** Shows user: complexity, estimated runtime, estimated searches, proceed Y/N  
**HITL:** Always — but lightweight (one confirm)  

---

### Stage 7 — Context Builder
**Agent:** Context Builder Agent  
**Model:** Sonnet  
**Skills:** `research-heuristics`  
**Tools:** Web search, Web fetch, MEDIA_REGISTRY.json read  
**Reads:** `Company_Memory.md` (freshness check), `INPUT.md`, `workspace/classifier.md`  
**Output:** `workspace/context.md`, updated `Company_Memory.md`  
**HITL:** None  

**Freshness check per field type:**

| Info type | Max age before refresh |
|---|---|
| Business model | 6 months |
| Leadership | 1 month |
| Product UI / flows | 2 weeks |
| Pricing | 2 weeks |
| Competitors | 1 month |
| App reviews | Always fresh |

---

### Stage 8 — Research Planning
**Agent:** Research Planner  
**Model:** Opus  
**Skills:** `research-heuristics`, `pm-frameworks`  
**Reads:** `workspace/intent.md`, `workspace/context.md`, `workspace/hiring_signal.md`  
**Output:** `workspace/research_plan.md`  
**HITL Checkpoint #2 (optional):** Show plan to user for approval before research runs.  

---

### Stage 9 — Parallel Research
**Agents:** Research Executor subagents (N parallel, Sonnet or Haiku by effort level)  
**Skills:** `research-heuristics`  
**Tools:** Web search, Web fetch, Vision (if media relevant), MEDIA_REGISTRY.json read  
**Each subagent gets:** One bounded question, explicit scope, output format, non-overlapping topic ownership  
**Each subagent reads:** MEDIA_REGISTRY → meta files → decides metadata-sufficient vs re-analyze  
**Output:** `workspace/research_<qid>.md` per question  
**HITL:** None during execution  

---

### Stage 9b — Research Gap Analysis + HITL
**Agent:** Orchestrator (inline lightweight call)  
**Reads:** All `workspace/research_*.md`, `workspace/research_plan.md`  
**Process:** Check findings against plan success criteria → summarize gaps  
**HITL Checkpoint #3 (always for extra research):** "Gaps found in X, Y. Approve additional research pass?"  
**If declined:** Proceed with gaps explicitly flagged in `workspace/open_questions.md`  

---

### Stage 10 — Insight Synthesis
**Agent:** Insight Synthesizer  
**Model:** Sonnet  
**Skills:** `pm-frameworks`  
**Reads:** `workspace/research_*.md`, `workspace/context.md`  
**Output:** `workspace/synthesis.md`  
**HITL:** None  

---

### Stage 11 — Case Builder
**Agent:** Case Builder  
**Model:** Sonnet  
**Skills:** `pm-frameworks`, `writing-style`, `presentation-style`, `hiring-signal-patterns`  
**Reads:** `workspace/synthesis.md`, `workspace/intent.md`, `workspace/context.md`, `workspace/hiring_signal.md`, `workspace/classifier.md`  
**Output:** `draft.json` (structured content object), `workspace/assumptions.md`, `workspace/recommendations.md`, `workspace/tradeoffs.md`  
**HITL:** None  

---

### Stage 12 — Devil's Advocate
**Agent:** Devil's Advocate  
**Model:** Sonnet (fresh context — not same instance as Case Builder)  
**Skills:** `pm-frameworks`, `hiring-signal-patterns`  
**Reads:** `workspace/recommendations.md`, `workspace/assumptions.md`, `workspace/synthesis.md`, `workspace/intent.md`  
**Output:** `workspace/devils_advocate.md`  
**Protocol:** One pass only. Case Builder does one revision pass on draft.json based on output.  
**HITL:** None  

---

### Stage 13 — Strict Checker
**Agent:** Strict Checker  
**Model:** Opus (fresh context, different from Case Builder)  
**Skills:** `checker-rubrics`  
**Tools:** Regex/grep (Tier 1 deterministic), File read  
**Reads:** `draft.json`, `workspace/intent.md`, `workspace/assumptions.md`, `workspace/research_*.md`, `workspace/hiring_signal.md`  
**Output:** `check_report.json`  
**HITL Checkpoint #4 (optional):** Human override for borderline verdicts.  
**Loop cap:** Max 2 correction loops. After 2 FAIL → HITL with best draft + unmet criteria list.  
**Loop detection:** Hash draft.json; if near-identical to prior attempt → stop + escalate.  

#### Checker rubric (3 tiers)

**Tier 1 — Hard gates (all must PASS, deterministic where possible):**
- Required output format present
- Every Intent Contract sub-question addressed (binary coverage checklist)
- Every quantitative claim has a citation field populated
- No placeholder text (grep: TODO, [INSERT], lorem, TBD)
- Assumptions Register present for ungrounded claims
- Hiring signal areas covered (mapped from workspace/hiring_signal.md)

**Tier 2 — Graded (≥ 0.8 each, LLM-scored with chain-of-thought):**
- Intent alignment
- Completeness
- Grounding/faithfulness
- Insight quality
- Internal consistency

**Tier 3 — Qualitative notes (advisory):**
- Audience/tone fit
- On-brand
- Format conventions

**Failure routing:**
- Missing evidence → Research Executor
- Good evidence, poor argument → Case Builder
- Scope mismatch → Intake + user re-clarify
- Format/consistency only → Formatter

---

### Stage 14 — Executive Review
**Agent:** Executive Reviewer  
**Model:** Sonnet  
**Skills:** `hiring-signal-patterns`  
**Reads:** `draft.json`, `workspace/hiring_signal.md`, `workspace/recommendations.md`  
**Output:** `workspace/executive_review.md`  
**Role:** Advisory only. Feedback visible to user at final review. Does not block pipeline.  
**HITL:** None  

---

### Stage 15 — Output Selection
**Agent:** Orchestrator  
**HITL Checkpoint #5 (always):** Present options → user selects formats → pass list to Formatter.  
**Exception:** If INPUT.md specified outputs upfront → skip this step, use those.  

**Options presented:**
- Executive Summary (1-pager)
- Slide Deck (PPTX)
- Speaker Notes
- Full Document (DOCX)
- Appendix / Backup Data
- FAQs
- Likely Interview Questions + Suggested Answers
- 30-second pitch script
- 5-minute walkthrough script

---

### Stage 16 — Formatter
**Agents:** Formatter subagents (one per selected format, Haiku)  
**Skills:** `presentation-style`, `brand-templates`  
**Tools:** PptxGenJS, DOCX generator, HTML renderer  
**Reads:** `draft.json` ONLY (single source of truth — all formats rendered from same object)  
**Output:** `OUTPUTS/<format_files>`  
**Gate:** Only runs on Checker PASS. Never renders a failing draft.  

---

### Stage 17 — Visual QA
**Agent:** Visual QA (fresh subagent, Haiku)  
**Tools:** Vision (renders output files to images), Regex/grep  
**Reads:** `OUTPUTS/` files  
**Checks:** Placeholders, broken images, layout, slide count, branding, filename  
**Output:** `qa_report.json`  
**Loop:** Issues → back to Formatter (not counted as Checker loop)  

---

### Stage 18 — Final Review
**HITL Checkpoint #6 (mandatory):** Presents all deliverables + qa_report + executive_review.  
**On approve:** `state.json` updated to `complete`. Company Memory updated with any new stable facts.  
**HITL:** Always.  

---

### Stage 19 — Optional Retrospective
**Agent:** Workspace Manager (if input provided)  
**Trigger:** Orchestrator nudges user max 2 times (tracked via `state.json.hitl_nudge_count`)  
**If provided:** Updates `MEMORY.md` → `Company_Memory.md` → `Global/memory/`  
**If declined after 2 nudges:** Skip silently.

## 11. Memory Architecture

### Three logical layers, two physical locations

**Physical:**
```
Assignment OS/
  Global/memory/          ← global learnings
  Companies/<Co>/
    Company_Memory.md     ← company learnings
    <Assignment>/
      workspace/          ← assignment memory (section files = the memory)
      MEMORY.md           ← reusable learnings summary for this assignment
```

**Global Memory** — generalizable across all companies:
- Presentation structure that works
- PM frameworks preference
- Writing voice + style
- Research heuristics learned
- Lessons from past assignments

**Company Memory** — reusable across assignments for same company:
- Business model, products, target market
- Competitors and positioning
- Known metrics and benchmarks
- Leadership priorities and style
- Previous assignments and outcomes
- Preferred deliverable formats
- Interviewer preferences (if known)
- Each field has: `last_verified`, `confidence`, `refresh_cadence`

**Assignment Memory** = the `workspace/` section files themselves. No extra layer.

## 12. Token Efficiency Architecture

| Principle | Implementation |
|---|---|
| Context contracts | Each agent declares exactly which workspace/ files it reads |
| Indexed retrieval | Agents read section files, never full WORKSPACE.md |
| Summaries | Every large artifact has `analysis_summary` in metadata; agents default to summaries |
| Single writer | Workspace Manager is only writer to workspace/ — no duplicate context loading |
| Composable prompts | One responsibility per prompt, assembled by orchestrator |
| Deduplication | Research Planner assigns exclusive topic ownership per subagent |
| Effort scaling | Complexity drives agent count; simple → 1 subagent; complex → N |
| Budget upfront | Execution budget shown to user before run |
